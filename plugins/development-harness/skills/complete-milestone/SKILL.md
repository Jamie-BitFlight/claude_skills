# Complete Milestone

Resolve the backend with `dh:backend-resolution`. Require a numeric milestone number; do not treat literal unsubstituted `$ARGUMENTS` as input.

1. Resolve the milestone by numeric `number`, using `state="all"` only to report missing/closed state.
2. Exhaust every configured-backend item page with `include_closed=true`; select only entries whose string `milestone_number` equals the resolved number string. Reconcile the native `state` (`OPEN`/`CLOSED`) membership counts against the milestone's reported open/closed counts before audit, projection, or close; workflow labels do not substitute for lifecycle state. Without MCP, load `dh:dh-cli-usage` and run its absolute `<sam_cli/> backlog list --include-closed` from the target cwd.
3. Present every matching item grouped by native lifecycle state. If native-open items remain, ask the user to carry each to a selected/new milestone, leave it unassigned only where supported, or close it through normal `backlog_close` lifecycle with a valid reason. Do not silently mark incomplete work done or use a raw helper.
4. Assign carried items with `backlog_assign_item_to_milestone` only after the target milestone exists and each assignment is confirmed. For an approved supported-backend unassignment, call it with that item's `issue_number` and explicit `milestone_number=null`; without MCP use `<sam_cli/> backlog assign-milestone --issue-number <issue> --clear`. Carrying requires the numeric target; use `<sam_cli/> backlog assign-milestone --issue-number <issue> --milestone-number <number>`. Stop closure on any unresolved disposition or count mismatch.
5. After the complete membership audit contains no open item, call `backlog_close_milestone(milestone_number=<requested number>)` (CLI: `<sam_cli/> backlog close-milestone --milestone-number <requested number>`). Preserve the backend result; unsupported is a stop, never a fallback.
6. Project V2 Done is an optional GitHub projection, separate from the configured-backend closure. Run it only after the successful milestone close and only when the resolved backend is `github`. For every candidate in the final native-`CLOSED` membership, retain the authoritative GitHub source identity returned by that backend: the canonical source repository and its numeric issue number. Never derive a GitHub target from a logical reference, selector, or numeric `issue` field on a SQLite/Memory/local item. If the resolved backend is not `github`, report projection as inapplicable and do not ask for projection configuration or invoke a helper. For GitHub candidates, ask for the Project V2 owner, project number, repository, and exact status value. The supplied `--repo` must exactly equal the candidate's authoritative source repository; the Project V2 owner may differ. On absent or unverifiable source identity, or a repository mismatch, stop and report that candidate's projection as inapplicable; do not invoke the helper or substitute another same-number issue. Resolve `GH_PROJECT_HELPER` to the absolute `github_project_setup.py` path in the loaded `gh` skill without changing the target project's cwd, then run `uv run "$GH_PROJECT_HELPER" project update-status --issue-number <authoritative GitHub issue number> --status "<status>" --project-number <project-number> --owner <owner> --repo <authoritative source repository>` once for every eligible final native-`CLOSED` GitHub issue. Report each helper result separately from the backend closure.
7. Report backend, milestone number, complete audit/count reconciliation, every disposition, closure result, and retained warnings/pending writes.
