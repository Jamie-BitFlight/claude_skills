Document Types current state

Every entity in the system is a document: structured text with metadata and relationships to other documents. These are currently stored, parsed, and rendered by three separate subsystems with no shared layer.

BacklogItem

GitHub Issue body (markdown) + frontmatter metadata. The primary unit of work. Contains sections of two kinds: entry sections (tracked items with IDs) and prose sections (freeform text). Sections are currently rendered inconsistently.

SAM Plan

YAML document listing tasks with dependencies, status, and metadata. Currently stored locally as .yaml files and written through to GitHub Gist. Treated as a separate system from BacklogItem despite being the same concept: structured text + metadata + relationships.

Task

A child of a SAM Plan. Has status, acceptance criteria, agent assignment, and relationships to sibling tasks. Stored inside the Plan YAML. Currently not a first-class document — cannot be queried or navigated independently.

Artifact

A registered output of a pipeline stage: feature-context, architect spec, codebase-analysis, T0-baseline, TN-verification. Stored as content in a GitHub Gist file. Referenced via a manifest entry on the associated issue.

Artifact Manifest

Per-issue index of all registered artifacts. Stored in the GitHub Issue body as a structured section. Parsed and written by ArtifactRegistry. Currently a separate parse path from normal issue body parsing.

Plan Index

Reverse map: plan_id → issue_number. Stored as a YAML blob on a sentinel GitHub Issue. Needed because SAM plan files use local IDs that are not the GitHub issue number. A translation layer that exists due to the two-system split.

Dispatch Plan

Wave-based execution plan for a milestone. YAML stored at plan/milestone-{N}-dispatch.yaml. Separate document type, separate storage, separate parse path.

Local YAML Cache

Translation of the GitHub Issue body into a local .yaml file. Added for human readability. Now consumed only by AI agents. Creates a permanent sync problem: the YAML can drift from the live GitHub body between syncs. Candidate for elimination.

Friction Map — Where Translation Breaks Down

Each item below is a place where the current architecture produces incorrect, inconsistent, or unpredictable results. These are root causes, not symptoms.

  • F1
    Zero-timestamp IDs are not unique When _build_sections_metadata parses a plain-text body (no <div> blocks), it calls parse_entries() in entry_blocks.py:158: entry_id = ts_match.group(1) if ts_match else f"{added_date}T00:00:00Z" where added_date defaults to "0000-00-00". Every unwrapped entry gets "0000-00-00T00:00:00Z" as its ID. Not unique. Breaks since filtering, deduplication, and struck tracking. Not a parsing limitation — a writer failure that the reader compensated for instead of fixing.
  • F2
    Two rendering formats, no enforcement Entry sections use <div><sub>timestamp</sub>...</div>. Prose sections use plain ## Header\n\ntext. No function enforces which format a section must use. 17 independent write sites each make their own choice.
  • F3
    _sections_from_body_or_yaml: two-path read logic Exists solely because the writer is inconsistent. If every section had a <div> block, this function reduces to one branch: parse blocks, return result. The subset check and YAML fallback are compensations for F1 and F2, not design.
  • F4
    YAML cache drifts from GitHub body The local .yaml file is written at sync time. The GitHub Issue body can be edited between syncs. Sections groomed by an agent appear in the live body before the YAML is updated. The reader has to decide which source to trust — there is no ground truth.
  • F5
    YAML was designed for human readers; AI reads it now The translation GitHub JSON → BacklogItem → YAML → BacklogItem exists because YAML is human-readable. The GitHub JSON response is already a valid cache. The YAML is an extra translation step that adds drift for no agent benefit.
  • F6
    Section name normalization is absent AI agents write section names freely: ## Impact Radius, ## impact-radius, ## Impact radius. No normalization at ingress. The same logical section exists under different keys in the same item depending on which agent wrote it.
  • F7
    BacklogBackend Protocol leaks raw strings render_issue_body() is a Protocol method that returns a raw markdown string. This means backends implement their own rendering logic. The Protocol boundary should only carry domain objects — BacklogItem in, BacklogItem out. Rendering belongs to the domain layer.
  • F8
    SAM and backlog are the same concept implemented twice Both store documents with metadata and relationships. Both need parsers, renderers, and cache strategies. They share no code and cannot reference each other's objects without a translation step. The Plan Index exists only because of this split.
  • F9
    Three artifact systems with independent parse paths Artifact Manifest is parsed from the Issue body. Plan content is parsed from Gist YAML. Dispatch Plan is parsed from local YAML. Each has its own parser and renderer. An agent navigating the full item → plan → task → artifact graph crosses three separate parse contexts.
  • F10
    Section parsing split across three modules with no shared abstraction operations.py — section boundary detection, metadata assembly, YAML fallback.
    rendering.py — groomed section rendering.
    entry_blocks.py — entry block parsing, ID generation, timestamp extraction.
    No unified navigator or section layer. Changes to section semantics require coordinated edits across all three. The zero-timestamp bug (F1) lives in entry_blocks.py but its consequences are handled in operations.py — two modules aware of the same broken contract.

Design constraints

One wire format for all sections

Every section — entry or prose — uses <div><sub>{id}</sub>content</div>. Prose sections have one entry. The Renderer decides the wire format. Callers call write_section(), never write raw headers.

No zero-timestamp IDs

ID = {issue.createdAt}-{section_name}-{position_index} when no explicit timestamp exists. Deterministic, non-colliding, correctly ordered relative to real timestamps. Zero-timestamp fallback is deleted entirely.

GitHub JSON as cache, not YAML

Cache the raw GitHub API response. Parse on demand: JSON → BacklogItem. One translation step, not five. YAML local storage eliminated. Drift between cache and source reduced to API response staleness only.

Section name normalization at ingress

The Parser normalizes section names to canonical keys before they enter the domain model. ## Impact Radius, ## impact-radius, ## Impact radius all map to impact_radius. The agent sees one key regardless of how it was written.

Protocol carries domain objects only

repository.get(id) → BacklogItem. repository.save(item: BacklogItem). No raw strings, no dicts, no markdown at the boundary. render_issue_body() moves out of the Protocol into the Renderer.

SAM and backlog share the document layer

Plan is a document. Task is a section of a Plan. BacklogItem is a document. Both use the same Repository, Parser, Renderer, Section Normalizer, and ID Generator. Plan Index eliminated — the plan is a relationship on the BacklogItem.

What gets deleted

  • DEL
    _sections_from_body_or_yaml() — two-path read logic replaced by one-path Parser at ingress
  • DEL
    _build_sections_from_yaml_item() — YAML is not a read source in the new model
  • DEL

  • DEL

Q2: Other format inconsistencies beyond prose vs entry?

A human or external agent edits a GitHub Issue body directly. It arrives without <div> blocks. The Parser must define a clear policy: normalize on read, reject, or flag?

Thousands of items exist in the old format. On first read: wrap in <div> using createdAt baseline, write back, return normalized form. One-time migration per item, not a permanent two-path read.

Design Revision updated after ensemble + reference reads

The original brief was wrong on one point

The brief proposed wrapping all sections (including prose) in <div> blocks. The ensemble found this breaks all 58 skills, all 28 agents, all documentation navigation, and the grooming contract. That change is off the table.

Revised understanding

Entry sections — correct format, not enforced

## Header + <div><sub>timestamp</sub>content</div> per entry. The format is right. The problem is 30+ write sites can bypass it and produce plain text. The reader then generates zero-timestamp IDs to compensate.

Fix: Enforce via one writer. Zero-timestamp fallback deleted. createdAt baseline used when timestamp unavailable — but only when the field is actually present (see Audit section: added_date defaults to "0000-00-00", so this is not always derivable).

Prose sections — correct format, intentional

## Header + plain text. Description, Groomed subsections, Story, Resolved — freeform text that should not get <div> wrappers. The ecosystem assumes this universally.

Fix: Keep as-is. Centralize the writer to prevent drift.

What the unified layer actually is

Not a new wire format. A single enforced write path with two methods, and a single parse path with no fallback:

class SectionWriter:
    def write_entry_section(name, entries):
        # Always: ## name + div blocks. No exceptions.

    def write_prose_section(name, text):
        # Always: ## name + plain text. No div wrappers.

class SectionParser:
    def parse(body):
        # One path: div blocks → entry section.
        # No blocks → prose section.
        # No YAML fallback. No zero-timestamp IDs.

Open questions that need answers before any ADR

Q1: Which sections are entry vs prose?

A registry is needed. What constitutes an entry section vs a prose section? Where does this registry live? What happens when an agent writes a new section name not in the registry?

Q2: Is createdAt always available?

parsing.py:106 shows added_date = _fm_str(...) or "0000-00-00" — the field is optional. The proposed createdAt + section + index baseline ID requires resolution of what to do when the field is absent.

Q3: Does the YAML cache serve a purpose beyond format?

The YAML cache is used as a performance optimization — _build_sections_from_yaml_item() avoids re-parsing the body. Eliminating it requires a replacement caching strategy, not just format change.

Q4: How does SAM share the writer?

SAM schema has 12+ independent write sites. Does sam_schema import from backlog_core? Currently there is no shared section code between them.

Logical fallacies in the design brief

  • FAL
    Genetic fallacy — "YAML was designed for human readability, therefore AI agents should not read it." The origin of a design choice does not determine its current validity. YAML also serves as a performance cache for section reads.
  • FAL
    False dichotomy — "Two formats exist therefore they must be unified under one format." The evidence shows the formats create complexity. It does not show that unification is the only fix — graduated enforcement or format detection are alternatives.
  • FAL
    Necessity fallacy — "Two-path read compensates for writer inconsistency, therefore the architecture must replace it, not wrap it." Replacement is one option. The brief rejects all wrapping with no cost-benefit analysis.
  • FAL
    Overgeneralization — "Zero-timestamp IDs are not unique, therefore they must be eliminated entirely." They cause problems when mixed with real IDs in since filtering. Isolation, conversion, or segregation are valid alternatives to elimination.
