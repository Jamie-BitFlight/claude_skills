## 2. Hooks

### Lifecycle events

Twelve events, enum `HookEventName` in `codex-rs/protocol/src/protocol.rs` lines 1576-1589 (read 2026-09-06): `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PreCompact`, `PostCompact`, `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `SubagentStart`, `SubagentStop`, `Stop`, `Interrupt`. Same twelve as config keys (`"PreToolUse"` ... `"Interrupt"`) in `HookEventsToml`, `codex-rs/config/src/hook_config.rs` lines 36-59, and as JSON-schema fixtures under `codex-rs/hooks/schema/generated/` (`post-tool-use.command.input.schema.json`, `stop.command.input.schema.json`, `subagent-stop.command.input.schema.json`, ...).

Handler types (`HookHandlerConfig`, `hook_config.rs` lines 163-200; wire enum `HookHandlerType` `protocol.rs` lines 1593-1598): `command` (`command`, `commandWindows`, `timeout` seconds, `async`, `statusMessage`, `additionalContextLimit`), `mcp_tool` (`server`, `tool`, `input`, `timeout`, `statusMessage`), `prompt` and `agent` (empty structs). Matchers: `MatcherGroup { matcher: Option<String>, hooks: Vec<HookHandlerConfig> }` (`hook_config.rs` lines 154-160); matcher is honoured for PreToolUse, PermissionRequest, PostToolUse, SessionStart, SessionEnd, SubagentStart, SubagentStop, PreCompact, PostCompact and ignored for UserPromptSubmit, Stop, Interrupt (`codex-rs/hooks/src/events/common.rs` lines 112-128). Matcher forms: empty or `*` = all; `[A-Za-z0-9_|]` only = exact with `|` alternatives; anything else = regex (`common.rs` lines 130-173). The hooks feature `CodexHooks` is `Stage::Stable`, `default_enabled: true` — `codex-rs/features/src/lib.rs` lines 1167-1170.

### Where hook config lives

Discovery walks every config layer low-to-high and loads, per layer, both `<config folder>/hooks.json` and the `[hooks]` table of that layer's `config.toml`; loading both in one layer emits a warning "loading hooks from both ... prefer a single representation" — `codex-rs/hooks/src/engine/discovery.rs` lines 129-165, `load_hooks_json` lines 339-364 (file name `"hooks.json"` line 343), `load_toml_hooks_from_layer` lines 382-400 (`layer.config.get("hooks")` line 387). `hooks.json` shape is `HooksFile { description?, hooks: HookEventsToml }` (`hook_config.rs` lines 12-17). Config folders: User layer = parent of `${CODEX_HOME}/config.toml`; Project layer = the `.codex/` folder — `codex-rs/config/src/state.rs` `config_folder()` lines 219-231, `hooks_config_folder()` lines 233-243 (linked git worktrees can point hook discovery at the root checkout's folder). Layer order: package, admin (MDM), system `/etc/codex/config.toml`, cloud, user `${CODEX_HOME}/config.toml`, profile, cwd `config.toml`, tree `./.codex/config.toml` up to root, repo `$(git rev-parse --show-toplevel)/.codex/config.toml` (project layers "loaded but disabled when untrusted"), runtime — `codex-rs/config/src/loader/mod.rs` lines 109-121. Hook source labels per layer: System, User, Project, Mdm, CloudManagedConfig, SessionFlags — `discovery.rs` lines 823-832. Managed hooks come from `requirements.toml` `managed_hooks` (`discovery.rs` lines 213-247; `ManagedHooksRequirementsToml` `hook_config.rs` lines 220-227).

**Do hooks fire inside the sub-agent?** Yes, for thread-spawned sub-agents (`SubAgentSource::ThreadSpawn`, `codex-rs/protocol/src/protocol.rs` lines 2825-2840). Each sub-agent is its own `Session` and builds its own hook config from the same layers (`build_hooks_config` called from `session/session.rs` line 1336 and `session/mod.rs` line 1930). In the child: SessionStart is replaced by `SubagentStart` (`hook_runtime.rs` lines 124-150: "Pending session-start hooks are reused to dispatch thread-spawn subagent starts"), Stop is replaced by `SubagentStop` (lines 383-425), SessionEnd does not run (lines 464-468: "SessionEnd is root-only"), and PreToolUse / PermissionRequest / PostToolUse / UserPromptSubmit / PreCompact / PostCompact / Interrupt run normally with the sub-agent context attached (`subagent: thread_spawn_subagent_hook_context(sess, turn_context)` at lines 194, 255, 297, 536, 573, 671). Internal sub-agents (`Review`, `Compact`, `MemoryConsolidation`, `Other`) run no user hooks (lines 148, 422-424).

**Distinct identifier?** Yes. `SubagentHookContext { agent_id, agent_type }` (`codex-rs/hooks/src/events/common.rs` lines 15-18) is filled with `agent_id = sess.thread_id().to_string()` — the sub-agent's own thread id — and `agent_type = agent_role or "default"` (`hook_runtime.rs` lines 1030-1036). These serialize as `agent_id` / `agent_type` in PreToolUse, PostToolUse, PermissionRequest, UserPromptSubmit (optional; absent for the root agent) and as required fields in SubagentStart/SubagentStop. Meanwhile `session_id` stays the root thread's id for every agent in the tree (`session/session.rs` lines 784-795: non-root agents take `agent_control.session_id()`), so root vs child is distinguishable by `agent_id` presence, and siblings by `agent_id` value. `ThreadSpawn` also records `parent_thread_id` and `depth` (`protocol.rs` lines 2828-2830), but those are not in hook payloads.

**Different working directory or git worktree?** Not via the tool. `spawn_agent` has no cwd/worktree parameter (arg structs above); the child config copies `config.cwd = turn.cwd` from the parent turn — `codex-rs/core/src/tools/handlers/multi_agents_common.rs` lines 237-265 (`let turn_cwd = turn.cwd.clone(); config.cwd = turn_cwd;` lines 251-252; doc comment lines 170-176: "inherit runtime-only state such as provider, approval policy, sandbox, and cwd"). Looked in `codex-rs/core/src/tools/handlers/multi_agents*.rs`, `multi_agents/`, `multi_agents_v2/` and `codex-rs/core/src/agent/` for `worktree`, `cwd`, `workdir` (grep, 2026-09-06): the only cwd handling is the inheritance above. A managed git worktree exists only as a whole-session CLI flag: `--worktree` "Run the session in a new managed Git worktree." — `codex-rs/utils/cli/src/shared_options.rs` lines 70-72, implemented in `codex-rs/tui/src/worktree_startup.rs` and the `codex-worktree` crate; it applies to the root session, not to spawned agents.
